# 高德限流与局部查询失败修复（2026-10-18）

## 问题与证据

用户提供的 `/api/assist` 响应为 `MAP_PROVIDER_ERROR / GROUNDING`。在修改前，使用同一份已解析输入、重建空 snapshot、全新进程缓存，直接复查地图阶段：前三次地点查询成功，第四次地点查询返回真实高德错误 `10021 / CUQPS_HAS_EXCEEDED_THE_LIMIT`。

原因为城市证据阶段并发搜索绕过了节流，后续酒店查询紧接着发送；同时，地图错误被直接向上抛出，导致可选查询或单一交通方式的失败也能终止整次规划。

## 本次修改

1. 删除 `paced` 绕过入口。所有真实高德请求（包含城市证据搜索和重试）都经过同一运行实例内的发送间隔控制，默认 500 ms，可使用服务端环境变量 `AMAP_REQUEST_INTERVAL_MS` 配置。
2. 对明确的瞬时 QPS、服务繁忙错误及 HTTP 429 增加最多一次重试。限流触发实例级冷却，其他排队请求也等待；HTTP 429 尊重 `Retry-After`。取消与总超时可中止排队、等待和请求。
3. 单条路线失败返回 `unavailable`，不再丢弃其他交通方式的有效结果。附近候选和实时天气可以标为未知/缺失，并在结果页提示。
4. 必要地点仍必须解析成功。所有允许的路线都失败时仍返回失败；生成的方案每一段仍须有新鲜的真实路线并通过原有 validators。账号密钥、签名、平台、认证问题及取消/总超时不降级。
5. 查询前继续应用用户交通限制，候选方案实体化时再检查允许名单。禁止步行时既不查询步行，也不能从意外出现的步行数据中兜底。
6. API failure 新增仅包含数字的 `providerCode`，保留高德错误码；服务端记录失败接口路径、错误码、尝试次数，以及真实出站次数和重试次数。记录不包含密钥、完整 URL、坐标或用户原文。

相关入口：`services/world/amap-client.ts`、`amap-routes-service.ts`、`amap-weather-service.ts`、`world-context-service.ts`、`services/deepseek-planner.ts`、`services/request-execution.ts`、`types/failures.ts`、`app/api/assist/route.ts`。

## 生效范围与部署

- 本次只修改本地源码，未提交、推送或部署。线上需要重新构建并部署才能生效。
- 默认 500 ms 是保守的实例内间隔，不代表已确认账号的全部配额。可以按高德控制台实际额度调大间隔。
- 调度器与冷却状态属于单个运行实例，不能保证多个 Vercel 实例、多个进程或本地与线上共用账号时的合计 QPS。需要全局配额保证时，应接入共享的原子限流或统一高德出站服务；本次没有新增这类基础设施。
- 用户限制仍由现有识别与允许名单负责。此次强化名单的执行，不宣称所有自然语言否定表达均已识别，也不宣称公共交通接驳完全不含步行。
