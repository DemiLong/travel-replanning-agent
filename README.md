# coveredYou · 接住临时变化，重新安排今天

下雨了、起晚了、景点关门了，或者原来的安排实在太赶——把接下来的行程和变化告诉 coveredYou，它会结合地点、路线和你的限制，尝试给出新的安排。

这是一个仍在迭代的单日行程调整应用。目前的主流程是匿名使用，行程保存在当前浏览器。你可以先创建今天的行程，也可以直接在首页说出原计划和遇到的问题，不必先填完一整张表。

> 当前支持范围：单日行程、以高德数据为基础的地点与路线查询。暂不提供多日规划、海外行程、预订、账号或跨设备同步。

## 先跑起来

需要 **Node.js 22.13 或以上版本**、npm，以及 DeepSeek 和高德 Web 服务密钥。

在项目根目录安装依赖：

```sh
npm ci
```

复制 `.env.example` 为 `.env.local`，填写以下配置。已有 `.env.local` 时直接编辑，不要覆盖原配置。

```dotenv
DEEPSEEK_API_KEY=你的DeepSeek密钥
DEEPSEEK_MODEL=deepseek-v4-flash
DEEPSEEK_BASE_URL=https://api.deepseek.com
AMAP_API_KEY=你的高德Web服务密钥
```

模型名是项目当前的默认配置，可换成账号实际可用的兼容模型。密钥只供服务端使用，不要加 `NEXT_PUBLIC_` 前缀，也不要提交到仓库。

`.env.example` 里保留了 Supabase 等历史配置；当前匿名浏览器主流程不依赖这些配置，无需为本地体验专门搭建数据库。

启动开发服务：

```sh
npm run dev
```

打开 [http://localhost:3000](http://localhost:3000)。修改环境配置后需要重启服务。缺少密钥时页面仍可打开，但真实解析与规划无法完成。

如果要运行生产构建：

```sh
npm run build
npm start
```

以上是当前主要使用的 Next.js 运行方式。仓库也保留了 Sites / vinext 的脚本，本地使用不需要切换到那套流程。

## 怎么使用

可以从首页直接输入，例如：

> 现在13:00，我在上海人民广场。原定15:00到16:00去上海国金中心，18:00到19:00去外滩，现在下雨了，请帮我调整。

具体时间、地点名称、必须保留的预约写得越清楚，系统越容易判断。例句只是输入示范，不保证每次都能得到可执行方案；结果还取决于实时路线、地点数据和模型输出。

通常会经历这几步：

1. **说明原计划和变化。** 已保存的行程会作为上下文参与调整；没有保存过行程，也可以先从输入建立本次草稿。
2. **补齐必要信息。** 比如酒店叫什么，或者同名地点究竟是哪一家。一次回答一个问题，答案更新对应活动，不重新解释整段原文。
3. **查看调整结果。** 有可用方案时进入结果页；信息不足、服务不可用和没有安全方案会分别提示。
4. **确认后保存。** 调整方案不会自动覆盖正式行程。接受结果时会再次校验，通过后才保存。

也可以先到创建页整理行程，再回首页处理变化。

| 页面 | 用途 |
| --- | --- |
| `/` | 描述变化，发起调整，回答补充问题 |
| `/onboarding` | 创建或编辑今天的正式行程，不自动规划 |
| `/trip` | 查看已保存的今日行程 |
| `/rescue` | 编辑复杂活动信息，或重新理解原文 |
| `/result` | 查看推荐与可能的备选方案，确认接受 |

`/replan` 是兼容入口，会跳转到 `/rescue`。

## 目前修到了哪里

最近几轮修改集中在输入理解、草稿续接和保存前校验：

- 重述已保存的预约时，没有再提供结束时间，应保留原来的时段和时长来源。
- “已经确定的安排”和“还在考虑的备选”分别处理，不能因为一句“全部来得及吗”就把备选强行加入行程。
- 接口返回无效 JSON、空值或不符合约定的对象时，前端显示受控提示，不直接拿异常数据继续保存。
- 确定活动缺地点时会先追问。地图层的活动地点文本补问按 `placeId` 精确对应活动，再将答案写回；无法唯一对应时停止，不猜测。
- 地点名称补充与地图候选选择保持各自的处理方式，避免修补文本回答时破坏 POI 选择。
- 规划没有有效结果时返回 `NO_SAFE_PLAN`，不会当作已有方案送进结果页。

最新地点补问修补已通过本地受控回归。此前也留有真实模型分类和空行程生成、接受、保存后刷新的测试记录；这些证据只覆盖各自的案例，不能代表所有输入或整个 P0 已验收。

修补记录见 [三个代码缺陷修补记录](docs/coveredYou-三个代码缺陷修补记录-2026-09-23.md)。其中“10/10”包含 8 条仅验证语义分类的测试，不是 10 条完整用户流程；固定预约案例最终为 `NO_SAFE_PLAN`，证明范围是预约信息保留，不能算生成新方案成功。

## 数据与使用限制

- 行程、草稿和待接受方案存放在当前浏览器的本地存储中。没有云端备份，清除浏览器数据或换设备后不能自动恢复。
- `localhost` 与 `127.0.0.1` 属于不同站点，浏览器里的行程不共享。开发时尽量固定使用一个地址。
- 本地保存不等于全程离线：语义解析和规划会把相关输入与行程上下文发送到模型服务，地点与路线查询使用高德。
- 固定预约和已完成活动有校验保护；保存时也会检查行程版本，避免直接覆盖另一标签页的修改。
- 高德基础地点信息不能证明商户此刻仍在营业。数据不足时，应用不能保证“赶得上”或“一定开放”。
- 服务存在超时和查询次数限制，补问也有轮次上限。得到“没有安全方案”是一次明确的失败结果，不代表行程已调整成功。

## 测试：分清验证了什么

日常代码检查和受控回归：

```sh
npm run typecheck
npm run lint
npm run test:unit
npm run test:e2e
```

`test:e2e` 会先构建，再启动测试服务。执行前请释放 **3000 端口**。首次缺少 Chromium 时，可以执行 `npx playwright install chromium` 安装浏览器。

| 测试 | 主要用途 | 不能据此得出的结论 |
| --- | --- | --- |
| `test:unit` | 验证草稿合并、地点回填、字段映射、预约保护、异常分支等；包含注入依赖的受控案例 | 不证明真实模型和地图能跑通 |
| `test:e2e` | 浏览器交互、响应结构校验、故障注入等受控回归 | 不证明真实文字到保存的完整链路 |
| `test:semantic-live` | 调用真实模型检查语义解析 | 不证明地图、规划和保存成功 |
| `test:world-live` | 真实服务联调脚本 | 不等同于浏览器完整操作 |
| `test:p0-live` | 真实浏览器与外部服务测试，包含不同验证范围的案例 | 通过数量不等于完整流程数量 |

真实服务测试需要有效密钥和网络，会消耗外部服务额度，按需手动执行：

```sh
npm run test:semantic-live
npm run test:world-live
npm run test:p0-live
```

`test:p0-live` 同样会构建并使用 3000 端口。测试实现位于 `live-e2e/`，部分案例的脱敏记录保存在 `work/three-defect-live-evidence/`。

记录验收结果时，请区分“答案已正确回填”“已生成方案”和“接受、保存、刷新后仍存在”。不要用预设成功响应代替真实服务验收，也不要把 `NO_SAFE_PLAN` 记成成功生成方案。

## 开发时从哪里看

主要技术栈是 Next.js、React、TypeScript、Zod、Tailwind CSS 和 Playwright。

```text
app/          页面与 API 路由
components/   创建、今日行程、补问、编辑和结果界面
agents/       调整流程编排与重规划
services/     语义解析、草稿处理、本地会话、模型和地图服务
validators/   时间、路线、固定安排及变更完整性校验
types/        数据结构与 Zod 校验约定
evals/        本地可靠性测试
e2e/          浏览器受控回归
live-e2e/     真实服务浏览器测试
scripts/      构建辅助、测试和联调入口
docs/         修补与验证记录
```

当前主要 API：

| 接口 | 用途 |
| --- | --- |
| `POST /api/parse` | 将自然语言整理为结构化事实 |
| `POST /api/assist` | 串联草稿、补问、地图查询和规划 |
| `POST /api/validate` | 接受调整结果前重新校验 |
| `GET /api/config` | 查询服务配置状态 |

`/api/assist` 的业务状态为 `READY`、`NEEDS_INPUT`、`OUT_OF_SCOPE`、`UPSTREAM_UNAVAILABLE` 和 `NO_SAFE_PLAN`。补问续接携带草稿、答案和问题状态；业务判断应检查返回结构与状态，不能只看 HTTP 200。

## 常见排查

**创建页突然 404：** 先确认当前运行目录、端口和 `/onboarding` 路由。项目曾出现过清理 `.next` 后恢复的情况，但这不能直接说明“缓存容量不够”。怀疑构建产物异常时，先停止服务，确认项目根目录后再清理 `.next` 并重启；不要清浏览器数据来处理构建问题。

**出现“服务暂时不可用”：** 查看服务端日志，区分配置缺失、网络问题、超时和上游返回异常。曾有 Node 24 测试进程未使用环境代理而无法连接的记录；只有实际使用代理且运行时支持时，才考虑配置 `NODE_USE_ENV_PROXY=1`，它不是所有环境的必填项。

**补充回答后仍无法继续：** 检查问题标识是否对应当前草稿活动，以及答案是否真正写回。测试要覆盖这个往返过程，不能只验证页面显示了问题。
